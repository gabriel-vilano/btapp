## Visão geral

Toast tem duas camadas:

- **`ToastVisual`** — componente apresentacional. Recebe `type`, `message`, `exiting`, `onDismiss` por props e renderiza o toast individual. É o que você vê na maior parte deste documento.
- **`ToastProvider` + `useToast`** — orquestração. Gerencia a fila, timing de auto-dismiss, exit animation. Você usa essas APIs pra disparar toasts no app real.

## Estados

Estados do toast individual: a saída animada e o botão de fechar em foco.

### Saindo

Quando `exiting=true`, o toast aplica animação de saída (fade + slide). Em produção dura ~170ms antes de ser removido do DOM.

<Canvas of={ToastStories.Exiting} />

### Fechar focado

O `X` focado pelo teclado mostra o ring de foco branco (`--color-state-focus-ring-on-strong`): o azul do ring padrão some sobre o fundo escuro do toast. A área tocável é de 48×48, mesmo com o ícone `sm`.

<Canvas of={ToastStories.DismissFocused} />

## Provider e hook

`ToastProvider` orquestra a fila de toasts; `useToast` expõe `showToast()` em qualquer componente abaixo.

### Auto-dismiss (padrão)

Toast some sozinho após 4s. Comportamento default — apropriado pra confirmações curtas.

<Canvas of={ToastStories.ProviderTriggers} />

### Persistente

`options.persistent: true` impede o auto-dismiss. Use pra mensagens que exigem leitura (instruções importantes, erros bloqueantes).

<Canvas of={ToastStories.ProviderPersistent} />

## Como usar

```tsx
// 1. Envolver a app com ToastProvider (uma vez, no layout root)
import { ToastProvider } from "@/src/components/ui/Toast";

export default function RootLayout({ children }) {
  return (
    <html>
      <body>
        <ToastProvider>{children}</ToastProvider>
      </body>
    </html>
  );
}

// 2. Em qualquer componente abaixo, usar o hook
import { useToast } from "@/src/components/ui/Toast";

function MyForm() {
  const { showToast } = useToast();

  async function handleSubmit() {
    try {
      await api.submit();
      showToast("Inscrição confirmada", "success");
    } catch {
      showToast("Falha ao confirmar — tente novamente", "error");
    }
  }
}
```

## Quando usar

- Confirmação de ação **transitória** que não precisa permanecer (criar, salvar, excluir)
- Erro **não-bloqueante** que o usuário pode ignorar e tentar de novo
- Notificação contextual ("Novo torneio publicado") sem interromper o fluxo

## Componentes relacionados

- Para **mensagem persistente** dentro do fluxo da tela, use [`Alert`](?path=/docs/ui-alert--docs)
- Para **erro de campo de formulário**, use a prop `error` do [`FormInput`](?path=/docs/ui-forminput--docs)

## Acessibilidade

- Cada toast tem `role="alert"` — leitor de tela anuncia imediatamente
- Botão de dismiss tem `aria-label="Fechar"`, `type="button"`, área tocável de 48×48 (maior que o ícone, sem aumentar o toast) e ring de foco branco, que contrasta com os três fundos do toast ([WCAG 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)). Hover e press usam state layer claro, porque o toast sempre tem fundo escuro
- Auto-dismiss em 4s pode ser curto pra leitores lentos — usar `persistent: true` quando o conteúdo for crítico
- Animação de entrada/saída usa `transition` curtas (170ms) — não interfere com `prefers-reduced-motion` significativamente, mas vale validar

## Evitar

- ❌ **Toast longo** — máximo ~6 palavras. Se a mensagem for grande, considere `Alert` ou modal
- ❌ **Toast pra erro de validação de campo** — usar a prop `error` do `FormInput`, que é contextual ao campo
- ❌ **Múltiplos toasts simultâneos da mesma ação** — debounce ou consolidar em uma só mensagem
- ❌ **Toast persistente sem botão de fechar visível** — o `X` deve ser óbvio, senão o usuário fica preso

## Decisões de design

**Por que `ToastVisual` separado de `ToastProvider`?**
Documentação. `ToastVisual` puro é renderizável com props mockadas em qualquer story — args panel funciona, variantes lado a lado, `exiting` controlável. Provider+hook continuam pra orquestração no app real, mas não são o que você quer documentar visualmente.

**Por que Provider + hook em vez de componente declarativo (`<Toast show={true}>`)?**
Toast é resposta a eventos (resultado de ação async), não estado da tela. Modelo declarativo forçaria cada componente a manter `useState` próprio do toast, multiplicando boilerplate. Provider centraliza renderização; hook reduz call site a uma linha (`showToast("OK", "success")`).
