## Visão geral

`AvatarUpload` permite o usuário escolher uma imagem do dispositivo e ver preview imediato. Aceita JPEG, PNG e WebP de qualquer tamanho: a foto é reduzida para no máximo 512px e recomprimida em JPEG antes do preview, e só então passa pelo `validateAvatar` (limite de 1MB). Em caso de falha, mostra erro inline e chama `onFileSelect(null)`.

## Anatomia

```
┌─────────────────┐
│   ┌─────────┐   │
│   │   ➕    │   │  ← área (placeholder ou preview)
│   └─────────┘   │
│ Adicionar foto  │  ← label (ou erro)
└─────────────────┘
```

- **área** — círculo de 96×96 com placeholder (ícone `+`) ou preview da imagem selecionada
- **badge** — quando há preview, ícone de câmera no canto inferior direito sinaliza "trocar"
- **label** — texto abaixo da área. "Adicionar foto" ou "Trocar foto" conforme o estado, ou mensagem de erro em vermelho

## Estados

`preview` e `error` são gerenciados internamente via `useState` — não aceita props pra forçar visualmente.

### Empty

Estado inicial. Sem imagem, sem erro. Clique abre o file picker do browser.

<Canvas of={AvatarUploadStories.Empty} />

### Foto grande

Foto de celular acima de 1MB. Em vez de recusar, o componente reduz a foto e entrega a versão reduzida (~100KB) para `onFileSelect`. É ela que vai para o servidor.

<Canvas of={AvatarUploadStories.LargePhoto} />

### Arquivo ilegível

Arquivo que declara ser imagem, mas o browser não consegue decodificar (corrompido ou com extensão trocada). Mostra "Não foi possível ler a foto. Tente outra imagem."

<Canvas of={AvatarUploadStories.UnreadableFile} />

> **Nota:** "Foto grande" e "Arquivo ilegível" chegam ao estado com preview e ao estado de erro simulando o upload (play function). Não há stories estáticas desses estados: exigiriam extrair a UI para um componente apresentacional.

## Quando usar

- Step 2 do signup (upload de foto após criar conta básica)
- Edição de perfil (trocar avatar existente)
- Em qualquer fluxo onde o avatar é único arquivo de imagem do usuário

## Acessibilidade

- Renderiza como `<div role="button" tabIndex={0}>` — acionável por teclado (Enter ou Space)
- `aria-label` dinâmico: "Adicionar foto de perfil" / "Trocar foto de perfil" conforme estado
- `<input type="file">` interno tem `tabIndex={-1}` — só é ativado via clique no wrapper
- Mensagem de erro aparece como texto inline (sem `role="alert"` por enquanto — limitação atual)
- Foco visível via `:focus-visible`

## Evitar

- ❌ **Esconder o erro depois de exibido** sem o usuário interagir — o erro precisa permanecer até o próximo upload
- ❌ **Permitir formatos não-validados** (HEIC, GIF) — `validateAvatar` é a fonte de verdade; expandir lá se precisar de novos formatos
- ❌ **Enviar o arquivo original em vez do que `onFileSelect` entrega** — o original pode ter vários MB e é recusado pelo bucket e pelo limite de body da server action
- ❌ **Usar pra upload de múltiplos arquivos** — esse componente é single-file; criar outro pra galeria

## Decisões de design

**Por que `role="button"` em `<div>` em vez de usar `<button>` real?**
O componente precisa de uma área visual circular grande (96×96) com layout interno (preview overlap + badge + label abaixo). `<button>` traz estilo padrão do browser que conflitaria — bordas, fundos, padding. Usar `<div role="button" tabIndex={0}>` + handlers de teclado dá controle total sobre a aparência mantendo semântica de botão pra leitores de tela.

**Por que validar antes de chamar `onFileSelect`?**
Centraliza a regra de aceitação no componente. Consumidores não precisam re-validar — se `onFileSelect` foi chamado com `File`, ele já é válido e já está reduzido. Se foi chamado com `null`, o usuário rejeitou (cancelou) ou validação falhou.

**Por que reduzir a foto no cliente em vez de aceitar arquivos maiores?**
O limite de tamanho existe em três camadas: a validação da tela, o bucket `avatars` e o body da server action (1MiB por padrão no Next). Aumentar o body vale para **toda** server action. Reduzir a foto no cliente mantém as três camadas em 1MB e ainda gasta menos dados móveis e armazenamento: um avatar exibido a 96px não precisa de uma foto de 4000px. O limite é 1.000.000 bytes, não 1MiB, para sobrar espaço no body para o resto do form.
