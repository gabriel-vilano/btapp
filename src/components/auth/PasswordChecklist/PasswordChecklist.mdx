## Visão geral

`PasswordChecklist` mostra os requisitos da senha em tempo real conforme o usuário digita. Cada regra tem três estados visuais: **pendente** (cinza, círculo vazio), **atendido** (verde, check) ou **erro** (vermelho, X — só após `submitted=true`). Componente puro/apresentacional — recebe `checks` calculados pelo consumidor.

<Canvas of={PasswordChecklistStories.AllPending} />

## Anatomia

```
☐ Mínimo 8 caracteres        ← pendente (cinza)
✓ Pelo menos uma letra        ← atendido (verde)
✗ Pelo menos um número        ← erro (vermelho, só com submitted=true)
```

- **icon** — círculo vazio (pendente), check preenchido (atendido), X preenchido (erro)
- **label** — texto fixo da regra. Visualmente decorativo (`aria-hidden`); a label semântica vai no `aria-label` do `<li>` com o estado

## Estados

A regra de transição: **enquanto o usuário digita** os pendentes ficam neutros (cinza). **Após submit** (`submitted=true`), os pendentes viram erros — sinaliza visualmente o que está bloqueando a submissão.

### Tudo pendente

Usuário ainda não digitou nada. Todos os 3 itens em estado neutro.

## Quando usar

- Junto a campo de senha em telas de signup ou redefinir senha
- Em formulários onde os requisitos não são óbvios sem documentação visual

## Componentes relacionados

- [`FormInput`](?path=/docs/ui-forminput--docs) com `type="password"` — o input cuja senha é validada
- `validatePassword` em `src/lib/validations.ts` — função que produz o objeto `checks` consumido por este componente

## Acessibilidade

- Renderiza `<ul aria-label="Requisitos de senha">` — leitor de tela anuncia o grupo
- Cada `<li>` tem `aria-label` no formato `"Mínimo 8 caracteres: atendido"` — estado é parte da label semântica
- O texto visual está em `<span aria-hidden="true">` — evita leitura duplicada (label semântica + visual)
- Ícone via `<Icon>` com `aria-hidden` automático (decorativo aqui)

## Evitar

- ❌ **Mostrar `submitted=true` sem o usuário ter clicado submit** — isso surpreende o usuário com erros vermelhos sem ação dele
- ❌ **Mudar a ordem das regras dinamicamente** — o usuário aprende a posição visual; mover causa fricção
- ❌ **Hardcoded de regras na UI** — `RULES` é fonte interna; pra mudar requisitos, ajustar `validatePassword` e o array `RULES` juntos

## Decisões de design

**Por que `submitted` é prop em vez de derivar de `checks`?**
"Pendente" e "erro" são visualmente diferentes mas semanticamente o mesmo (não atendido). A diferença é o **timing**: antes do submit, o usuário ainda está construindo a senha — pendente neutro é apropriado. Depois do submit, é uma falha — erro vermelho é apropriado. Sem essa prop, o componente não saberia qual cor usar.
